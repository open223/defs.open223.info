# defs-open223-info

Source for <https://defs.open223.info>, the stable-identifier landing page for
ASHRAE 223P concept definitions.

`ontologies/223p.ttl` is the only committed input. Everything the site serves
is generated from it by `.github/workflows/build-site.yml`, which on every
push builds `index.html`, attaches it to the run as a downloadable artifact,
and deploys it to GitHub Pages from `main`. Updating the site means committing
a new `223p.ttl`; nothing generated is checked in.

## Contents

| Path | Purpose |
| --- | --- |
| `ontologies/*.ttl` | Published ontology files, served at `/ontologies/...`. `223p.ttl` is the single input to the site. |
| `publication-anchors.txt` | The anchors the publication document links. Regenerated by `make sync`, checked by `make check-anchors`. |
| `index.html` | The generated site. Not committed; built by `make` and published by CI. |
| `constraints.json` | Concept definitions and stable IDs extracted from `ontologies/223p.ttl`. Not committed; an intermediate of `make`. |
| `templates/` | Jinja template and static assets inlined into `index.html`. |
| `constraints.py` | Port of `publication/constraints.py` from the 223standard repo: finds each concept's SHACL constraints and rules and assigns stable IDs. |
| `build_constraints.py` | Writes `constraints.json` from `ontologies/223p.ttl`. |
| `make_site.py` | Renders `index.html` from `constraints.json`. |
| `anchors.py` | Records the publication's anchors (`extract`) and verifies the built page defines them (`check`). |
| `check-links.{sh,py}` | Checks that publication links point at anchors that exist. Needs a 223standard checkout; `make check-anchors` is the offline equivalent CI runs. |
| `tests/` | Regression tests for the stable-ID scheme (`make test`). |

## Stable IDs

The publication links to `<site>#<stable_id>`, so the IDs generated here must
match the ones generated by the 223standard publication build. (`<site>` is
`S223_DOC_HOST` in `ttl2md.py`; nothing here depends on its value.) Both use the same scheme, implemented in `constraints.py`:

- Named resources use their prefixed name, e.g. `s223:Equipment`.
- Blank-node constraints use `b-<label>` where the label comes from
  [RDFC-1.0](https://www.w3.org/TR/rdf-canon/) canonicalization
  (the [`rdfcanon`](https://pypi.org/project/rdfcanon/) package), e.g. `b-c14n42`.
  These depend only on the structure of the graph, so the same graph produces
  the same IDs no matter how it was serialized, parsed, or ordered.

Canonical labels are numbered across *all* blank nodes in the input graph, so
the two sides agree only when they canonicalize the same graph: keep
`ontologies/223p.ttl` a copy of `publication/223p_publication.ttl` (see
[Updating the site](#updating-the-site)), not the compiled `223p.ttl`, and keep
`constraints.py` in sync with its upstream copy.

`constraints.json` carries an `ontology` key with the `owl:versionInfo` of the
ontology declaration in `223p.ttl`; `index.html` displays it at the top of the
page so it is clear which build of the ontology the definitions came from.

## Updating the site

The site's anchors and the publication's links are both blank-node labels
canonicalized over a whole graph, so they only agree when both come from the
*same* graph. That graph is `publication/223p_publication.ttl`, written by
`ttl2md.py` during a 223standard publication build.

```sh
# 1. build the publication (in the 223standard checkout)
cd ../223standard && bash build-publication.sh && cd -

# 2. copy the graph that build minted the document's links from, and record
#    the anchors the document expects
make sync                  # or: make sync STANDARD=/path/to/223standard

# 3. commit the two files make sync wrote, and push
git add ontologies/223p.ttl publication-anchors.txt && git commit && git push
```

That is the whole update. CI builds `index.html`, fails if any of the
document's anchors are missing from it, and publishes to
<https://defs.open223.info>.

### Taking index.html elsewhere

Every link in the generated page is a bare fragment and its CSS and JavaScript
are inlined, so the same `index.html` works unchanged at any base URL. To put
it on another host, open the latest run of **Build index.html** under the
repository's Actions tab and download the `site` artifact — `index.html`, the
`ontologies/` directory it serves, and `CNAME`. That is byte-for-byte what
GitHub Pages deploys.

### Building locally

Needs [uv](https://docs.astral.sh/uv/); it installs the Python in
`.python-version` on first run.

```sh
make                       # constraints.json, then index.html
make check-anchors         # every anchor the publication links resolves
make test                  # stable-ID regression tests
make dist                  # assemble site/ exactly as CI uploads it
make serve                 # preview on :8000
make check                 # full link check; needs the 223standard checkout
```
